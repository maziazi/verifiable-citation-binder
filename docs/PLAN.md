# PLAN — Verifiable Citation Binder

**Source of truth #1.** This document governs *scope* and *sequencing*.
`docs/SPEC.md` governs behavior. If the two disagree, fix this one first.

**Execution budget: 120 minutes of AI-agent-driven development, solo.**
Everything below is sized to that constraint. Nothing in the concept has been
dropped — the full guarantee set, the full taxonomy, the full threat model, and
all three demo scenarios survive. What has been compressed is *how much is built
by hand* versus *how much is delegated*, and how deeply each piece is polished.

---

## 1. Feature classification: core vs delegable

The 120-minute budget is spent entirely on **core**. Delegable work is generated by
an agent in bulk and reviewed, not authored.

### Core — must be built and personally verified

These are the things a judge will press on, and the things that are wrong if an
agent guesses at them.

| # | Capability | Why it is core |
|---|---|---|
| C1 | Canonical serialization + SHA-256 digest | Every integrity claim reduces to this being exactly right |
| C2 | Hash-chained append with `seq` + sidecar head | G3 and G4 live here |
| C3 | Chain verification with failure localization | The demo's "Verify Ledger" button is this function |
| C4 | Tamper simulation (50 cases, 3 classes) | Scenario 2 and 3 are this; the 100% claim depends on it |
| C5 | Four-pillar composition + band assignment | The score model; BLACK override is subtle and easy to get wrong |
| C6 | 18-code taxonomy as a closed enum with strict parsing | G5 collapses into free text without this |
| C7 | Claim verification legend applied to every number | The difference between a research artifact and a pitch deck |

### Delegable — agent-generated, human-reviewed

| # | Capability | Review gate |
|---|---|---|
| D1 | Chunking + in-memory vector retrieval | Spot-check that retrieval returns the planted evidence |
| D2 | Sentence segmentation into claims | Eyeball 10 segmentations on the corpus |
| D3 | Adjudication prompt + strict response parsing | Read the prompt once; confirm the parser rejects an unknown code |
| D4 | Synthetic corpus (100 items, labelled) | Confirm label balance and that the canonical AMBER case is present |
| D5 | Streamlit viewer, three routes | Confirm all three scenarios are reachable in under 30 seconds each |
| D6 | Evaluation harness + metric computation | Confirm the metric definitions match §3 of this document |
| D7 | Test suite scaffolding | Confirm the Tier-1 tests run with no API key |
| D8 | CI/CD configuration | Confirm it is green before the deadline, not after |
| D9 | Report figures and tables | Confirm every number traces to `results/` |

### The division, stated as a rule

> An agent may write anything. A human must personally verify everything in the
> **core** list, and must read the diff for `src/vcb/core/` line by line. The core
> is small on purpose — roughly 400 lines — so that this is actually possible.

## 2. Milestones

Nine milestones, dated to a 120-minute budget. Minutes are wall-clock from start.

| # | Milestone | Window | Minutes | Exit criterion |
|---|---|---|---|---|
| M1 | **Skeleton** — repo, package layout, `pyproject.toml`, CLI entry point, empty tiers | 0–10 | 10 | `uv run vcb --help` prints the command list |
| M2 | **Tier 1 core** — canonicalization, digest, record model, append, verify | 10–30 | 20 | `uv run pytest tests/core` green, no network |
| M3 | **Attack simulation** — 50 cases, 3 classes, localization assertion | 30–45 | 15 | `uv run vcb attack` reports 50/50 detected, all localized |
| M4 | **Corpus** — 100 synthetic items with ground-truth labels | 45–55 | 10 | `corpus/` loads; label distribution printed and balanced |
| M5 | **Tier 2 adjudication** — retrieval, segmentation, model call, strict parsing, cache | 55–80 | 25 | One answer end-to-end produces a valid ledger of ≥4 records |
| M6 | **Scoring** — four pillars composed, bands assigned, BLACK override wired | 80–90 | 10 | The §4.5 worked example reproduces score 70 / AMBER exactly |
| M7 | **Viewer** — Streamlit, three routes, the three demo scenarios | 90–105 | 15 | A cold reader reaches each scenario unaided in <30s |
| M8 | **Evaluation** — harness runs on the corpus, writes `results/` | 105–115 | 10 | `results/metrics.json` and `results/cost.json` exist and are committed |
| M9 | **Submission** — README numbers tagged, report assembled, CI green, tag cut | 115–120 | 5 | `v0.1.0` tagged; CI green on `main`; report PDF ≤8 pages attached |

### Milestone dependency graph

```
M1 ──► M2 ──► M3 ──────────────────────┐
        │                              │
        └──► M6 ◄── M5 ◄── M4          ├──► M8 ──► M9
                     │                 │
                     └──► M7 ──────────┘
```

M3 depends only on M2, so the integrity story — the part that is provable and the
part a judge can rerun offline — is complete at the 45-minute mark. This ordering
is deliberate: if the budget overruns, the thing that survives is the thing that is
actually verifiable.

### The hard checkpoint

**At minute 45, M3 must be done.** If it is not, cut M7 to a single route and M8 to
20 corpus items, and continue. Do not cut M3 — a submission with a strong integrity
proof and a thin viewer is defensible; the reverse is not.

## 3. Success criteria

The project is complete when all three demo scenarios run and all four metrics are
measured and tagged.

### 3.1 The three demo scenarios

| # | Scenario | Action | Expected observable |
|---|---|---|---|
| S1 | **Decorative citation caught** | Open the demo answer containing the 20%-vs-5% claim | That claim renders AMBER with reasons `S02` + `N01` and an explanation naming both numbers |
| S2 | **Tampering caught** | Edit one character in `audit_ledger.json`, click **Verify Ledger** | Status turns BLACK, reports `L03` and the exact record index |
| S3 | **Omission caught** | Delete one record from the middle of the file, re-verify | Status turns BLACK, reports `L01` + `L02` and localizes the gap |

Each scenario must be executable by a judge in under 30 seconds, from a cold start,
with no API key.

### 3.2 The four metrics

| # | Metric | Definition | Target | Tag on report |
|---|---|---|---|---|
| E1 | **Detection precision** | Of claims VCB flags non-GREEN, the fraction that are genuinely unsupported per ground truth | Report, do not target | `[M]` |
| E2 | **Detection recall** | Of genuinely unsupported claims, the fraction VCB flags non-GREEN | Report, do not target | `[M]` |
| E3 | **Tamper detection rate** | Of the 50 attack cases, the fraction detected *and* correctly localized | **50/50 required** | `[M]` |
| E4 | **Reason coverage** | Fraction of scored claims carrying ≥1 valid taxonomy code and a span-referencing explanation | **100% required** | `[M]` |

E1 and E2 are **reported, not targeted**. Setting a precision target in advance and
then hitting it is how a hackathon project quietly becomes a demo of its own corpus.
The honest artifact is the measured number plus the error analysis of what it missed.

E3 and E4 *are* targets, because both are deterministic properties of the
implementation. Missing either is a bug, not a result.

### 3.3 Baseline comparison

The evaluation runs the same corpus twice:

- **Arm A — bare RAG.** Answer plus citations, no binding. Every claim is implicitly
  GREEN because nothing checks it.
- **Arm B — RAG + VCB.** Full binding and banding.

The comparison is not "is Arm B more accurate" — both arms produce the same answers.
The comparison is: **how many unsupported claims pass through unflagged in each
arm.** In Arm A that number is 100% by construction, which is the whole point. The
measured quantity is how far Arm B reduces it. `[M]`

## 4. Scope that was cut

Recorded so the cuts are visible as decisions rather than as oversights.

| Cut | Rationale | Where it would go |
|---|---|---|
| **C2PA signing** | C2PA adds a credential format and key management on top of a hash chain that already delivers G1/G3/G4. Within 120 minutes it would consume the entire Tier-1 budget and strengthen no guarantee we claim. | Post-hackathon; pairs naturally with the T6 anchoring work |
| **External datasets (AVeriTeC, RAGTruth)** | Download, schema inspection, and label mapping would cost 30–40 minutes of a 120-minute budget. The loader interface is specified in SPEC §5.4 and left unexercised. | First post-hackathon milestone; it is the single highest-value follow-up |
| **Local NLI model (DeBERTa-v3)** | ~800 MB download plus torch install exceeds the entire budget. The API adjudicator is the decision; the offline-determinism requirement is met by Tier 1, not by the adjudicator. | A hybrid local+API adjudicator is the natural v2 |
| **OpenTelemetry instrumentation** | Real value for production observability, zero value for the three demo scenarios. The ledger *is* the trace for our purposes. | Production hardening |
| **Blockchain / transparency-log anchoring** | The correct answer to T6, and far beyond the budget. Stated as an open limitation rather than half-implemented. | SPEC §11 item 2 |
| **Multi-hop claim verification** | Requires a reasoning-chain representation VCB does not have. Out of scope by design (SPEC §1.3). | Research direction, not an engineering task |
| **Weight tuning sweep** | Needs a labelled corpus large enough to avoid overfitting; ours is 100 synthetic items. Tuning on it would produce a number that means nothing. | Requires the external-dataset work first |
| **Prompt-injection test suite** | Genuinely needed (SPEC §8.1) and genuinely does not fit. Disclosed as a residual risk. | Security hardening pass |
| **Concurrent-writer ledger** | Single-writer is correct for a demo and honest about its constraint. | Production hardening |

## 5. Solo working rules

The constraint is one person with an agent and two hours. These rules exist to stop
the two most expensive failure modes: rework, and discovering at minute 110 that
nothing integrates.

1. **Branch per PR, merge fast.** No branch lives longer than one milestone. A
   long-lived branch under a two-hour budget is just an unmerged rewrite.

2. **Tier 1 is reviewed by hand, always.** Every line of `src/vcb/core/`. It is
   ~400 lines; this costs minutes and protects every claim in the submission.

3. **Tiers 2 and 3 are reviewed by behavior.** Read the tests and run the demo. Do
   not line-read agent-generated retrieval or Streamlit code.

4. **The demo runs end-to-end at every milestone boundary from M5 onward.** If it
   does not run, fix that before starting the next milestone. An integration failure
   found at minute 110 is unrecoverable; the same failure at minute 80 is a
   ten-minute fix.

5. **Tag every number the moment you write it.** Retrofitting the `[M]`/`[A]`
   legend across a finished README is a 20-minute job that will not get done.

6. **Cut scope, never cut verification.** If the budget slips, the viewer loses
   routes and the corpus loses items. The attack simulation, the chain verifier,
   and the reason-code enforcement do not shrink.

7. **Commit `results/` artifacts.** Reproducibility is a submission requirement.
   A metric that lives only in a terminal scrollback does not exist.

8. **Write the limitations section before the results section.** It is the section
   most likely to be skipped under time pressure and the one that most distinguishes
   research from marketing.

## 6. What "done" looks like

A public GitHub repository containing:

- **Source** that a judge can run with one command (`uv run vcb demo`) and verify
  offline with another (`uv run vcb verify audit_ledger.json`).
- **A sealed example ledger** (`audit_ledger.json`) committed at the repo root,
  plus the fixture ledgers the attack simulation runs against.
- **`results/`** with `metrics.json`, `cost.json`, and `attack.json`, each
  regenerable by a named command.
- **A report**, ≤8 pages: problem, mechanism, results, error analysis, limitations.
- **A viewer**, runnable locally with `uv run streamlit run app.py`.
- **`LICENSE.md`** — PolyForm Noncommercial 1.0.0.

And a statement a reviewer can check rather than trust: *every number in the README
carries a tag, and every `[M]` tag names the command that produces it.*
